# Архитектурные договорённости

Документ фиксирует принципы, которыми руководствуемся при развитии SpecSPDS. Это ориентиры для новых изменений, а не требование немедленно переделать существующий код.

## Внедрение зависимостей (DI)

1. Новые обычные классы по возможности проектируются с **constructor injection**: необходимые зависимости передаются через конструктор.
2. Существующий код переводится на DI постепенно, по мере работы над ним. Не проводить массовый рефакторинг только ради устранения старого подхода.
3. Не передавать контейнер по цепочке вызовов и не использовать Service Locator вместо обычного внедрения зависимостей.
4. Регистрации добавляются в `AddOnCompositionRoot` по необходимости. Не требуется регистрировать каждую команду nanoCAD как таковую.
5. Не вводить новый статический глобальный провайдер зависимостей в качестве простой замены `AddOnCtx`.

## Команды nanoCAD

1. Методы с `[CommandMethod]` остаются совместимыми с механизмом вызова nanoCAD и служат тонкими адаптерами.
2. Самостоятельную логику команды, особенно использующую сервисы или требующую тестирования, при необходимости переносить в обычный обработчик с зависимостями через конструктор.
3. Не создавать отдельный обработчик для каждой команды автоматически: решение зависит от сложности и ответственности команды.

## AddOnCtx

1. На текущем этапе `AddOnCtx` сохраняется.
2. Новые классы не должны получать через него зависимости, если их можно передать через конструктор.
3. Использование `AddOnCtx` сокращается постепенно, в рамках конкретных задач.
4. Удаление `AddOnCtx` целиком или изменение архитектуры композиционного корня требует отдельного обоснования и согласования.

## Ограничения изменений

- Предпочитать минимальные изменения в рамках текущей задачи.
- Не расширять объём рефакторинга без предварительного согласования.
- Сохранять совместимость с хостом nanoCAD и существующими контрактами.
- После изменений проверять сборку и относящиеся к изменению тесты; недоступные или невыполненные проверки явно отмечать.
